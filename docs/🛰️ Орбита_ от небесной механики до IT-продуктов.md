**1. Физика / астрономия**
Орбита — это замкнутый или открытый путь, по которому одно небесное тело движется вокруг другого под действием гравитации. Например, Земля вращается вокруг Солнца по эллиптической орбите, а Луна — вокруг Земли.

**2. Искусственные спутники**
Орбиты спутников классифицируют по высоте и наклону:
- **Низкая околоземная (LEO)** — 160–2000 км (МКС, спутники связи Starlink)
- **Средняя (MEO)** — 2000–35 786 км (навигация GPS/ГЛОНАСС)
- **Геоstationарная (GEO)** — 35 786 км (спутники связи и ТВ)
- **Полярная / солнечно-синхронная** — для разведки и наблюдения Земли

**3. IT-контекст**
«Орбита» — название различных продуктов и компаний:
- **Orbit** — платформа для управления данными и аналитикой
- **Orbital** — различные стартапы в области AI и автоматизации

#### ⚙️ Как работает платформа (на примере «Управление выгодой»)

**Промо-платформа (Catmanx + Whatif):**

1. **Сквозная автоматизация** — от поставщика до полки (offline + online каналы)
2. **ИИ-аналитика** — максимизация IRR промо, превращение в точку роста категории
3. **Интеграция кабинетов** — кабинет поставщика + кабинет коммерсанта
4. **Платформизация ДТО** — для двух сетей (ТСХ + ТС5)
5. **Автораспродажи** — автоматическое создание распродаж

**Технологический стек:**
- **Backend:** Java 11→21, Spring Boot 3.3.3, Postgres 12
- **Frontend:** TypeScript, React 17, Redux Toolkit
- **Data Science:** Python 3.7, PySpark 2.4.4, Airflow 2.6.3, Redash 8.0
- **DE:** Python 3.11, Trino 442, Airflow 2.8.1

**Инфраструктура:** 4 стенда (разработка → тест → демо → прод)

1. **ТОРГ** — основная ERP-система для управления ценами, квотами и ассортиментом. Интеграции двусторонние: и отправка данных в ТОРГ, и получение из него.

2. **SAP** — система высшего уровня (финансы, учёт). Интеграции через SAP PI (промежуточный шлюз), с расписанием отправок по DAG'ам.

4. **JDA** — система demand planning, используется для расчёта флорпланов.

5. **Связка SAP ↔ ТОРГ** — существует отдельная интеграция между SAP и ТОРГ, что создаёт цепочку: Орбита → ТОРГ → SAP.

**Пользователь я хочу понять как это работает все вместе. ВЕдь в ТОРГ , SPA есть свои ролевые модели, получается и в Орбите есть своя ролевая модель, кроме того ролевые модели есть и у продуктов. Эти роли как-то интегрированы между собой? или как это работает?**

Ассистент:На основе анализа документов в Confluence (спейс "Орбита"), вот как устроена интеграция ролевых моделей между системами:

### 🏗 Архитектура ролевой модели

**Единый источник ролей — Active Directory (АСУД)**

Все системы (ТОРГ, SAP, Орбита и продукты Орбиты) используют **группы в AD** как единый источник определения ролей пользователя.

### 🔗 Как это работает

#### 1. Роли в AD-группах
Каждая бизнес-роль привязана к группе в Active Directory. Например, из страницы "[Управление выгодой] Ролевая модель":

| Роль | Группа в AD | Роль в ПШ (Платформа Орбиты) |
|------|-------------|------------------------------|
| КМ ЦО | `whatif-category-manager-central` | ТС5: `ZCER2_X5056_PROMOTMPL_KM_CO_Y` / ТСХ: `ZCER2_X5052_PROMOTMPL_KM_CO_Y` |
| КМ ПФ | `whatif-category-manager-macro` | ТС5: `ZCER2_X5056_PROMOTMPL_KM_DIV_Y` / ТСХ: `ZCER2_X5052_PROMOTMPL_KM_DIV_Y` |

#### 2. Bridge Legacy — сервис получения ролей
Существует спецификация **SA_2724711 "Получение ролей и разрешений для пользователя через Bridge Legacy"** — это технический слой, через который приложения Орбиты запрашивают роли пользователя. Bridge Legacy выступает как шлюз к AD.

#### 3. Ролевые модели конкретных систем
- **ТОРГ (ТС5)** — своя ролевая модель (страница "Ролевая модель ТС5", v56, владелец Буровцев Вячеслав)
- **ТОРГ Холдинг (ТСХ)** — отдельная ролевая модель ("Ролевая модель ТСХ")
- **СAP** — имеет собственную ролевую модель (упоминается в контексте)
- **Продукты Орбиты** — каждый продукт (Управление выгодой, ЛККМ, NMATCH) имеет свою матрицу ролей

#### 4. Интеграция с АСУД
Документ **"БФТ Интеграция Платформы АЦО с АСУД"** описывает техническую интеграцию платформы Орбиты с Active Directory User Data. Также есть требования **"Требования к управлению правами доступа в ЦО ТСЧ (интеграция ЦО ТСЧ и АСУД) для MVP"**.

### 📌 Итог
Ролевые модели **НЕ объединены в единую централизованную матрицу** — каждая система/продукт имеет свою модель. Однако **интеграция обеспечивается через AD**:
1. Роли определяются как группы в AD
2. Bridge Legacy предоставляет API для получения ролей
3. Каждая система маппит свои внутренние роли на AD-группы
4. АСУД выступает как единый каталог пользователей
